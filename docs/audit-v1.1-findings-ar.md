## 1. الخلاصة التنفيذية

الحالة الحالية ليست تنفيذًا لنظام Wasl v1.1؛ بل هي تطبيق v6/legacy يعمل فوق `app_state` و`user_profiles` ومسارات Serverless قديمة، مع إضافة ترحيل علائقي جديد غير مكتمل وغير مستخدم من التطبيق. الترحيل نجح في إنشاء جزء من الجداول والدوال، لكنه لم يتبعه بناء Backend v1 أو واجهة تستخدمه أو خطة ترحيل بيانات فعلية.

**الحكم العام: غير جاهز للاعتماد أو التشغيل كنظام v1.1.**

أخطر نتيجة هي وجود فجوة بين ما توثقه المواصفة وما ينفذه النشر: التطبيق المنشور يعيد `200` على `/api/health` القديمة، لكنه يعيد `404` على `/health` و`/health/deep` و`/api/v1/referrals` و`/api/v1/metrics`. كما أن جدول `users` وجدول `referrals` العلائقيان فارغان، بينما `app_state` يحتوي سجلًا واحدًا و`user_profiles` أربعة سجلات؛ أي أن البيانات التشغيلية الفعلية ليست في نموذج v1.

## 3. النتائج التفصيلية

### F-01 — التطبيق الفعلي ليس Backend v1.1

- **الخطورة:** حرجة.
- **التصنيف:** نقص تنفيذ جوهري وتعارض مباشر مع المعمارية المعتمدة.
- **الدليل:** لا يوجد `backend/src` ولا `frontend/`. التنفيذ الفعلي موزع على `api/*.js` وواجهة ضخمة في `public/index.html`. `backend/server.js:1-27` يعرّف خادمًا قديمًا فقط ويعطل بعض المسارات بحالة `410`.
- **المواصفة ذات الصلة:** `docs/wasl-spec-v1.1.md:39-97` تطلب API Gateway وخدمات تطبيقية وخدمة Workflow فوق PostgreSQL، و`docs/migration-v1.1.md:11-14` تشترط بناء `/api/v1` قبل قطع القديم.
- **الأثر:** لا توجد طبقة خدمات موحدة تفرض العقد والصلاحيات والانتقالات المطلوبة؛ إضافة الترحيل وحدها لا تغيّر سلوك النظام.

### F-02 — النشر لا يقدم مسارات v1 أو مسارات الصحة المطلوبة

- **الخطورة:** حرجة.
- **الدليل من HTTP Production:**
  - `GET /api/health` → `200`، جسم قديم `{ok, service, time}`.
  - `GET /health` → `404`.
  - `GET /health/deep` → `404`.
  - `GET /api/v1/referrals` → `404`.
  - `GET /api/v1/metrics` → `404`.
  - `GET /api/state` → `401`، ما يثبت أن المسار القديم ما زال المسار التشغيلي.
- **الدليل في المستودع:** `api/health.js:1-4` ينشئ `/api/health` فقط؛ لا يوجد `api/v1` ولا `health/deep` ولا metrics.
- **الأثر:** المراقبة، التكاملات، واختبارات قبول v1 ستفشل؛ ونجاح Vercel لا يعني نجاح النظام المطلوب.

### F-03 — التطبيق لا يقرأ الجداول العلائقية الجديدة

- **الخطورة:** حرجة.
- **الدليل:** `api/state.js:24-38` يقرأ `public.app_state`، و`api/attachment.js:92-106` يقرأ الإحالات والمحادثات من JSON داخل `app_state`. `api/_auth.js:8-10` يقرأ `user_profiles`.
- **دليل قاعدة البيانات:** عدد الصفوف: `app_state=1`, `user_profiles=4`, `users=0`, `referrals=0`, `referral_v1_events=0`, `beds=0`.
- **الأثر:** `users`, `referrals`, `beds` وغيرها ليست مصدر الحقيقة الفعلي؛ الوظائف الجديدة لا يمكنها خدمة بيانات التشغيل الحالية.

### F-04 — دالة الانتقال تسمح بانتقالات غير مسموحة

- **الخطورة:** حرجة.
- **الدليل:** `database/migrations/017_wasl_v1_1_relational_core.sql:189-210` يتحقق من `version` وبعض حالات `completed` و`doctor_rejected` فقط، ثم ينفذ أي قيمة `p_to_status` دون مقارنة زوج `(current_status, next_status)` بمصفوفة انتقالات.
- **المقارنة:** المواصفة `docs/wasl-spec-v1.1.md:603-650` تحدد جدول انتقالات وأدوارًا لكل انتقال، وتطلب التحقق من الحالة المتوقعة، صلاحية الدور، القرار الإلزامي والإشعار ضمن معاملة واحدة.
- **أمثلة أثر:** يمكن تمرير انتقالات غير موجودة في الجدول، مثل نقل إحالة من `awaiting_doctor` إلى `completed` أو من `awaiting_bed` إلى `doctor_rejected`، ما لم تمنعها قيود خارجية غير موجودة.

### F-05 — دالة الانتقال SECURITY DEFINER قابلة للتنفيذ من PUBLIC

- **الخطورة:** حرجة.
- **الدليل من صلاحيات PostgreSQL:** `public.wasl_transition_referral(uuid,integer,wasl_referral_status,text,text)` لها `PUBLIC:EXECUTE` و`postgres:EXECUTE`.
- **الأثر:** الدالة ذات `SECURITY DEFINER` منشورة للتنفيذ العام. صحيح أنها تستدعي `current_wasl_user_id()` وترفض actor الفارغ، لكن إبقاء EXECUTE العام يوسع سطح الهجوم ويخالف مبدأ منح أقل صلاحية، خصوصًا مع غياب مصفوفة الانتقالات.
- **الإجراء المطلوب لاحقًا:** سحب EXECUTE من `PUBLIC` ومنحها فقط لمسار الخادم/الدور المقصود، مع تثبيت صلاحيات RPC ومراجعة كل دوال `SECURITY DEFINER`.

### F-06 — عقد الانتقال لا يطبق `expected_status` ولا Idempotency

- **الخطورة:** حرجة.
- **الدليل:** الدالة تقبل `p_expected_version` و`p_request_id` فقط؛ لا يوجد `expected_status`. جدول `wasl_idempotency_keys` موجود، لكن لا تستخدمه الدالة ولا يوجد endpoint v1 يحفظ أو يعيد نتيجة الطلب المكرر.
- **المواصفة:** `docs/wasl-spec-v1.1.md:625-652` تطلب `expected_status` وتسجيل الحدث والتدقيق والإشعار كعملية واحدة، و`:670-677` تطلب `Idempotency-Key` للعمليات القابلة لإعادة الإرسال.
- **الأثر:** إعادة إرسال الطلب أو اختلاف الحالة بين جهازين قد يؤدي إلى سلوك غير متطابق أو انتقال غير مقصود؛ وجود الجدول دون منطق استعمال ليس تنفيذًا للخاصية.

### F-07 — الانتقالات لا تنفذ RBAC الكامل ولا قواعد العمل الطبية

- **الخطورة:** حرجة.
- **الدليل:** الفحص في `017...sql:202-204` يقيد `doctor_rejected → completed` فقط. لا يوجد تحقق أن الطبيب هو `assigned_doctor_id`، ولا أن `beds` ينفذ قرارات الأسرة فقط، ولا أن المنسق/المدير يغلقان الحالات المسموحة فقط.
- **المواصفة:** `docs/wasl-spec-v1.1.md:468-496` و`:603-623` تحددان صلاحيات كل انتقال ودورًا بعينه، و`:523-540` تمنع الطبيب من الإغلاق الإداري.
- **الأثر:** يمكن لدور صحيح المصادقة أن ينفذ عملية صحيحة شكليًا لكنها غير صحيحة وظيفيًا.

### F-08 — لا توجد إشعارات v1 ولا outbox ذرية

- **الخطورة:** عالية.
- **الدليل:** `017...sql` لا ينشئ `notifications` جديدة مرتبطة بسير v1 ولا `notifications_outbox`، ودالة الانتقال لا تضيف إشعارًا. فحص القاعدة أثبت غياب `notifications_outbox`.
- **المواصفة:** `docs/wasl-spec-v1.1.md:647-650` تطلب إنشاء الإشعار ضمن المعاملة، و`:771-780` تحدد API الإشعارات والمحادثات.
- **الأثر:** انتقال الحالة قد ينجح دون إعلام الدور التالي، أو لا توجد وسيلة موثوقة لإعادة محاولة التسليم.

### F-09 — مخطط v1 ناقص عن الحقول والأنواع والقيود المرجعية

- **الخطورة:** عالية.
- **الدليل:** `017...sql:39-67` يعرّف `admission_type varchar(30)` و`doctor_decision varchar(30)` بدل أنواع/قيود قيم معتمدة؛ لا يوجد `latest_consultation_id`؛ لا توجد دالة `next_ref_no()`؛ `ref_no` مجرد حقل `NOT NULL UNIQUE`.
- **المواصفة:** `docs/wasl-spec-v1.1.md:287-315` تتطلب حقول قرار واستشارة كاملة، و`:711-739` تتطلب توليدًا خادميًا لرقم مثل `WASL-YYYY-NNNNNN`.
- **الأثر:** لا يوجد ضمان لتنسيق الرقم المرجعي أو لقيم القرارات، وقد تتراكم استشارات دون مؤشر آخر استشارة.

### F-10 — لا يوجد منع قاعدة بيانات لتعديل الإحالة المكتملة

- **الخطورة:** عالية.
- **الدليل:** `017...sql:39-67` لا يحتوي trigger أو constraint يمنع تعديل حقول إحالة حالتها `completed`. الحماية موجودة جزئيًا داخل الدالة فقط، ولا تغطي تحديثات أخرى عبر service role أو مسارات مستقبلية.
- **المواصفة:** `docs/wasl-spec-v1.1.md:24-35` و`:625-652` تشترطان انتقالًا موحدًا وأرشفة/إلغاء موثقًا وعدم الكتابة فوق التاريخ الطبي.
- **الأثر:** قد تصبح الحالة المكتملة قابلة للتعديل خارج مسار الانتقال، ما يضعف سلامة السجل الطبي والتدقيق.

### F-11 — سياسات RLS v1 غير مكتملة للكتابة والجداول التشغيلية

- **الخطورة:** عالية.
- **الدليل:** الترحيل ينشئ سياسات SELECT فقط للجداول الأساسية في `017...sql:224-229`. لا توجد سياسات مكتملة للإدراج والتعديل لطلبات الأسرة والمرفقات والإشعارات والمستخدمين؛ المسار البديل هو `service_role`، لكن لا يوجد Backend v1 يطبق التفويض المطلوب.
- **الأثر:** إما أن عمليات v1 لا تعمل عبر JWT للمستخدمين، أو ستضطر إلى service role واسع الصلاحية داخل كود غير موجود/غير موحد.

### F-12 — المصادقة الفعلية مرتبطة بـ `user_profiles` لا بجدول `users` v1

- **الخطورة:** عالية.
- **الدليل:** `api/_auth.js:8-10` يستخرج الملف من `user_profiles`، و`api/login.js:17-30` يبحث عن `employee_number` في `user_profiles` ثم ينشئ cookies. بينما `017...sql:25-37` يعرّف `users` بحالة enum `pending/active/rejected/disabled`.
- **الأثر:** تفعيل/تعطيل/رفض الحساب في نموذج v1 لا يتحكم في الجلسة الفعلية؛ يوجد مصدران متوازيان للحسابات والصلاحيات.

### F-13 — عقد الاستجابة الموحد غير مطبق

- **الخطورة:** عالية.
- **الدليل:** `api/state.js:154-199` و`api/login.js:6-43` يعيدان أشكالًا مثل `{error: ...}`, `{ok: true}`, `{authenticated: true}` بلا `success/data/meta` وبلا `meta.request_id`. `api/auth-requests-approve.js:21-88` يستخدم `request_id` داخل الجسم فقط وبشكل غير موحد.
- **المواصفة:** `docs/wasl-spec-v1.1.md:804-847` تحدد غلاف النجاح والخطأ، ورموز HTTP، ومعرّف الطلب.
- **الأثر:** العملاء لا يستطيعون الاعتماد على عقد واحد، ولا يمكن ربط كل عملية بسجل تدقيق/تشخيص موحد.

### F-14 — المرفقات الفعلية legacy وليست `/referrals/:id/attachments`

- **الخطورة:** عالية.
- **الدليل:** `api/attachment.js:92-106` يقرأ الإحالات من `app_state`، و`:164-227` يعالج سياقًا مخصصًا قديمًا، و`:230-276` يعمل عبر endpoint واحد غير مطابق لمسارات v1. التنزيل يعيد bytes مباشرة بدل رابط Signed URL قصير.
- **المواصفة:** `docs/wasl-spec-v1.1.md:753-769` تطلب مسارات v1، فحصًا، Bucket خاصًا، Signed URLs، وسجل رفع/تنزيل/حذف.
- **الأثر:** لا توجد واجهة تشغيلية مرتبطة بـ `referral_attachments` العلائقي، ولا سجل v1 مكتمل للتنزيل، كما أن مسار legacy يظل جزءًا من السطح التشغيلي.

### F-15 — المحادثات والرسائل تعتمد جداول قديمة وعقودًا غير موحدة

- **الخطورة:** عالية.
- **الدليل:** `api/conversations.js:10-27` و`api/messages.js:22-46` يستخدمان `conversations`, `conversation_members`, `conversation_messages` القديمة، ويعيدان أجسامًا مثل `{messages}` و`{message}` مباشرة.
- **المواصفة:** تطلب محادثات مرتبطة بالإحالات وصلاحية العضوية وعقود `/api/v1` الموحدة. وجود الجداول القديمة ليس المشكلة وحده؛ المشكلة أن لا توجد طبقة v1 تربطها بالمخطط المعتمد أو تطبق العقد.

### F-16 — طلبات التسجيل القديمة تعيد إنشاء مصدر حسابات موازٍ

- **الخطورة:** عالية.
- **الدليل:** `api/auth-requests.js:26-45` و`api/auth-requests-approve.js:35-81` يستخدمان `auth_requests` و`user_profiles` ويستعملان حالة `processing` أثناء التنفيذ، بينما جدول v1 `users` يستخدم enum حالة مختلفًا ولا توجد عملية مزامنة إلى `users`.
- **الأثر:** اعتماد طلب تسجيل قد ينشئ Auth و`user_profiles` فقط، ويترك `users` فارغًا؛ بالتالي لا يستطيع نظام v1 العثور على المستخدم أو دوره.

### F-17 — جدول `auth_requests` محمي بالـ RLS لكن بلا سياسات استخدام للمستخدمين

- **الخطورة:** متوسطة إلى عالية.
- **الدليل:** `database/002_employee_auth_requests.sql:39-41` يفعّل RLS ويسحب الصلاحيات من `public, anon, authenticated` ويمنح `service_role` فقط. هذا متوافق مع استخدام خادمي محدود، لكنه يصبح فجوة وظيفية لأن التطبيق الجديد غير موجود، كما أن بقية الجداول القديمة لا تشارك نفس نموذج الصلاحيات.
- **ملاحظة:** لا يُعد غياب سياسة عامة ثغرة بحد ذاته هنا؛ الخطر هو اعتماد المسار على service role مع غياب طبقة v1 موحدة ومراجعة تفويض مركزية.

### F-18 — CI لا يختبر v1 ولا يعمل على push إلى main

- **الخطورة:** متوسطة إلى عالية.
- **الدليل:** `.github/workflows/security-regression.yml:3-8` يشغل push فقط على `fix/security-hardening-followup-2026-11`، و`:17-20` يشغل security scan واختبارات أمنية قديمة فقط. `package.json:5-10` لا يحتوي build أو اختبارات قبول v1 أو typecheck أو migration verification.
- **الأثر:** يمكن دمج/نشر تغييرات على `main` دون فحص عقود v1 أو صحة البناء أو التوافق مع القاعدة.

### F-19 — إعداد Vercel لا يعلن routing أو build/backend v1

- **الخطورة:** متوسطة.
- **الدليل:** `vercel.json:1-31` يحتوي Cache-Control headers فقط. لا توجد قواعد `/api/v1/*` أو container/backend build أو health path.
- **الأثر:** إعداد النشر الحالي يفسر استمرار Serverless القديم وعدم وجود خدمة Backend v1 مستقلة؛ لا يكفي لتلبية البنية المطلوبة.

### F-20 — اختبارات المتصفح لا تختبر النشر أو Supabase أو عقد v1

- **الخطورة:** متوسطة.
- **الدليل:** `tests/app_browser_test.py` (وفق الفحص) يشغل خادم HTTP محليًا وحالة JSON محاكاة، و`tests/security/hardening_contracts.test.cjs` يختبر عقودًا قديمة مرتبطة بـ `app_state`. لا توجد اختبارات `/api/v1`, JWT, RLS, transition matrix, idempotency أو الإنتاج.
- **الأثر:** نجاح الاختبارات الحالية لا يعطي دليل قبول للنظام المقصود.

### F-21 — الحالة القديمة لا تزال متاحة كمسار تعديل جماعي

- **الخطورة:** متوسطة.
- **الدليل:** `api/state.js:162-185` يسمح `PUT/POST` بحفظ كامل JSON إلى `app_state` عبر `save_app_state`. الوثيقة نفسها (`docs/wasl-spec-v1.1.md:792-800`) تصفه كمسار قديم لا يعادل REST الجديد، و`docs/migration-v1.1.md:5` تقول إنه مجمد إلى حين القطع، لكن النشر ما زال يعرضه فعليًا.
- **الأثر:** يبقى مصدر حقيقة متوازٍ يمكنه تغيير بيانات تشغيلية خارج جداول v1، وتستمر احتمالات التعارض والتجاوز بين النموذجين.

## 4. نقاط إيجابية مؤكدة

- حالة Git نظيفة ومتزامنة مع `origin/main` على commit المفحوص.
- فحوص JavaScript النحوية نجحت.
- `npm run security:scan` نجح، و`git diff --check` نجح.
- ترحيل `017_wasl_v1_1_relational_core.sql` موجود ومسجل كتطبيق ناجح.
- الجداول العلائقية الأساسية والأنواع وبعض سياسات RLS ودوال الوصول موجودة.
- `api/_auth.js` يتحقق من Supabase Auth ولا يعتمد وحده على بيانات المتصفح.
- مسار `api/state.js` يستخدم optimistic revision في المسار القديم، لكن هذا لا يعوض `version/expected_status/Idempotency-Key` المطلوبة في v1.

## 5. ترتيب الإصلاح المقترح قبل أي اعتماد
